# Plz-Job 프로젝트 설명 (Phase 0~4)

> 이 문서는 **코드를 보지 않아도** plz-job 백엔드가 "무엇을, 왜, 어떻게" 하는지 이해할 수 있도록 쓴 안내서입니다.
> Phase 0(기반 설정)부터 Phase 4(문서 관리)까지 **현재 구현된 기능 전부**를 다룹니다.

---

## 1. 한 줄 소개

**Plz-Job** = 개발자 취업 준비생을 위한 **"취업 공고 · 지원 기록 관리 + 데이터 분석"** 플랫폼.

취업 준비를 하다 보면 이런 일이 생깁니다.

- 어제 지원한 회사가 어디였더라? 마감일이 언제였지?
- 이 회사는 서류 합격이었나, 코딩테스트에서 떨어졌나?
- 내 이력서 v1, v2, v3 중에 이 회사엔 뭘 냈더라?

Plz-Job은 이 모든 걸 **한 곳에서 기록하고 추적**합니다. 단순히 공고를 스크랩만 하는 게 아니라,
**지원 → 서류 → 코딩테스트 → 면접 → 최종**까지 이어지는 전형의 **전 과정**을 따라갑니다.
(나중 단계에서는 여기 쌓인 데이터로 "나 vs 채용 시장" 비교 분석까지 합니다.)

---

## 2. 기술 스택

| 구분 | 사용 기술 | 한마디 설명 |
|------|-----------|-------------|
| 백엔드 | Spring Boot 3.5 / Java 17 | 서버 본체 |
| DB | Oracle (JPA · Hibernate) | 데이터 저장. 자바 객체 ↔ 테이블 자동 매핑 |
| 인증 | Spring Security + JWT | **소셜 로그인 전용** (카카오·구글). 자체 회원가입 없음 |
| 파일 | Apache PDFBox + Jsoup | PDF 텍스트 추출 / 공고 URL 미리보기 |
| AI | 로컬 LLM (Ollama) | *Phase 5 이후* — 면접 질문 생성 등 |
| 프론트 | React | *별도 영역* |

> 🤔 **왜 소셜 로그인만 쓰나요?**
> 비밀번호를 직접 저장하면 그만큼 보안 책임이 커집니다. 카카오·구글에 인증을 맡기면
> 비밀번호를 우리 서버가 아예 갖고 있지 않아도 되어 더 안전합니다. (요구사항 §12.1)

## 3. 전체 동작 흐름 (사용자 시나리오)

실제 사용자가 어떤 순서로 기능을 쓰는지 따라가 봅시다.

```
 ① 카카오로 로그인          →  Phase 1 (인증)
        │
        ▼
 ② "네이버 백엔드 공고" 등록  →  Phase 2 (공고 등록)
    (URL 붙여넣기 → 자동 채움)
        │
        ▼
 ③ 서류 합격! 단계 변경       →  Phase 3 (지원 단계 추적)
    APPLIED → DOCUMENT_PASS
        │
        ▼
 ④ 이력서 PDF 업로드          →  Phase 4 (문서 관리)
        │
        ▼
 ⑤ "이 이력서를 네이버에 냈다" →  Phase 4 (공고-문서 연결)
    문서 ↔ 공고 연결
```

이 흐름을 떠받치는 **보이지 않는 기반**(공통 응답 형식, 인증 검사, 에러 처리)이 **Phase 0**입니다.

## 4. Phase 0 — 모든 기능을 떠받치는 4개의 기둥

Phase 0은 화면에 보이는 기능이 아니라, **나머지 모든 Phase가 공통으로 쓰는 토대**입니다.

### 기둥 ① 일관된 응답 봉투 — `ApiResponse<T>`

모든 API는 **똑같은 모양의 JSON**으로 답합니다. 프론트엔드 입장에서 "어디는 이렇고 저기는 저렇고"가 없어 편합니다.

```json
{
  "success": true,
  "data": { "원하는 결과": "..." },
  "error": null,
  "timestamp": "2026-06-19T10:00:00+09:00"
}
```

실패할 때는 이렇게 옵니다.

```json
{
  "success": false,
  "data": null,
  "error": { "code": "JOB_POSTING_NOT_FOUND", "message": "공고를 찾을 수 없습니다." },
  "timestamp": "2026-06-19T10:00:00+09:00"
}
```

### 기둥 ② 에러를 한 곳에서 처리 — `ErrorCode` + `GlobalExceptionHandler`

에러 상황마다 **고유 코드 + 사용자용 메시지 + HTTP 상태**를 미리 정해 둡니다.
서비스 코드는 그냥 `throw new CustomException(ErrorCode.JOB_POSTING_NOT_FOUND)` 한 줄만 던지면,
`GlobalExceptionHandler`가 알아서 위의 실패 JSON으로 바꿔 줍니다.

| 코드 예시 | 상태 | 뜻 |
|-----------|------|-----|
| `UNAUTHORIZED` | 401 | 로그인이 필요함 |
| `JOB_POSTING_NOT_FOUND` | 404 | 공고 없음 (또는 남의 공고) |
| `DOCUMENT_NOT_FOUND` | 404 | 문서 없음 (또는 남의 문서) |
| `UNSUPPORTED_FILE_TYPE` | 400 | PDF/TXT 외 파일 |
| `DUPLICATE_JOB_URL` | 409 | 이미 등록한 공고 URL |

### 기둥 ③ "내 것만 본다" — 소유권 검증

내 지원 기록을 **남이 볼 수 없어야** 합니다. 그래서 모든 조회/수정은
"이 리소스가 **정말 이 사용자 것인지**"를 먼저 확인합니다.

> 🤔 **남의 데이터를 요청하면 왜 403이 아니라 404인가요?**
> "권한 없음(403)"이라고 답하면 *"그 번호의 데이터는 존재하는구나"*가 노출됩니다.
> "없음(404)"으로 답하면 존재 여부조차 숨길 수 있어 더 안전합니다. (AUTH-06)

### 기둥 ④ 지우지 않는 삭제 — Soft Delete (`BaseEntity`)

삭제 버튼을 눌러도 DB에서 **진짜로 지우지 않습니다.** 대신 `deleted_at`에 삭제 시각을 적습니다.
모든 엔티티는 `@SQLRestriction("deleted_at IS NULL")` 덕분에 **삭제된 행은 조회에서 자동으로 빠집니다.**

> 🤔 **왜 진짜로 안 지우나요?**
> 실수로 지웠을 때 복구할 수 있고, "언제 무엇을 지웠는지" 기록이 남습니다.
> 모든 엔티티가 상속하는 `BaseEntity`에 생성/수정 시각(`createdAt`, `updatedAt`)과 `deletedAt`이 들어 있습니다.

## 5. Phase 1 — 로그인 (인증)

> **한마디**: 카카오·구글 계정으로 로그인하고, 내 취업 희망 정보(직무·지역·기술스택)를 관리한다.

### 엔드포인트

| 메서드 | 경로 | 하는 일 |
|--------|------|---------|
| GET | `/api/auth/oauth2/{provider}` | 카카오/구글 **로그인 페이지 주소**를 받아옴 |
| GET | `/api/auth/oauth2/{provider}/callback` | 로그인 성공 후 돌아오는 곳. **JWT 쿠키 발급** |
| POST | `/api/auth/reissue` | 액세스 토큰이 만료되면 **재발급** |
| POST | `/api/auth/logout` | 로그아웃 (쿠키 무효화) |
| GET | `/api/users/me` | 내 프로필 조회 |
| PUT | `/api/users/me/profile` | 내 프로필 수정 |

`{provider}` 자리에는 `kakao` 또는 `google`이 들어갑니다.

### 로그인은 이렇게 흘러갑니다

```
[사용자]                [우리 서버]              [카카오]
   │  ① 로그인 버튼          │                      │
   │ ───────────────────────►│                      │
   │  ② 카카오 로그인 주소     │                      │
   │ ◄───────────────────────│                      │
   │  ③ 카카오에서 로그인 ───────────────────────────►│
   │                         │   ④ "이 사람 맞음" + code │
   │ ◄───────────────────────────────────────────────│
   │  ⑤ code 들고 callback    │                      │
   │ ───────────────────────►│  ⑥ code로 사용자 정보 요청 │
   │                         │ ────────────────────►│
   │                         │  ⑦ 이메일·닉네임 등     │
   │                         │ ◄────────────────────│
   │  ⑧ JWT를 쿠키로 발급      │                      │
   │ ◄───────────────────────│ (가입 안 했으면 자동 가입) │
```

> 🤔 **JWT를 왜 쿠키에 담나요?**
> 토큰을 자바스크립트가 읽을 수 있는 곳(localStorage)에 두면 XSS 공격에 탈취될 수 있습니다.
> **HttpOnly 쿠키**에 담으면 자바스크립트가 아예 못 읽어서 더 안전합니다. 브라우저가 요청마다 자동으로 실어 보냅니다.

### User 엔티티 (사용자 한 명의 정보)

| 필드 | 설명 |
|------|------|
| `provider` | `KAKAO` 또는 `GOOGLE` |
| `providerUserId` | 카카오/구글이 부여한 고유 ID |
| `email` | 이메일 |
| `nickname` | 닉네임 (로그인 시 자동 설정) |
| `desiredPosition` | 희망 직무 (예: "백엔드 개발자") |
| `desiredRegion` | 희망 지역 (예: "판교") |
| `techStacks` | 보유 기술 목록 (예: `["Java", "Spring"]`) |

> `provider` + `providerUserId` 조합이 **유일(unique)** 합니다. 즉 같은 카카오 계정으로 두 번 가입되지 않습니다.

## 6. Phase 2 — 공고 등록·관리

> **한마디**: 취업 공고를 등록한다. URL만 붙여넣으면 회사명·제목을 자동으로 채워 준다.
> 공고를 등록하면 그에 딸린 **"지원 기록(Application)"이 자동으로 하나 생긴다.**

### 엔드포인트

| 메서드 | 경로 | 하는 일 |
|--------|------|---------|
| POST | `/api/job-postings/preview` | URL을 분석해 **미리보기**(회사명·제목·설명) 반환 |
| POST | `/api/job-postings` | 공고 등록 (+ 지원 기록 자동 생성) |
| GET | `/api/job-postings` | 공고 목록 (페이지네이션 · 단계별 필터) |
| GET | `/api/job-postings/{id}` | 공고 상세 |
| PUT | `/api/job-postings/{id}` | 공고 수정 |
| DELETE | `/api/job-postings/{id}` | 공고 삭제 (soft delete) |

### 핵심 개념: 공고(JobPosting)와 지원(Application)은 분리되어 있다

```
JobPosting (공고)              Application (지원 기록)
─────────────────             ──────────────────────
회사명, 제목, URL,             현재 단계(currentStage),
직무, 지역, 마감일,            최종 결과(finalResult),
기술스택, 본문,                지원 시각(appliedAt),
즐겨찾기                       단계 변경 이력(histories)
        └──────── 1 : 1 ────────┘
```

> 🤔 **왜 둘을 나눴나요?**
> "공고"는 *회사가 낸 객관적 정보*(안 바뀜)이고, "지원 기록"은 *내가 진행하는 주관적 상태*(계속 바뀜)입니다.
> 성격이 다르니 분리합니다. 그래서 공고를 등록하는 순간 짝이 되는 지원 기록이 **자동으로 함께 생성**됩니다.

### URL 미리보기 (preview)

공고 URL을 주면 서버가 그 페이지를 열어 **`og:title`(제목), `og:site_name`(회사명), `og:description`(설명)** 을 긁어옵니다. (Jsoup 라이브러리 사용)

- 다 찾으면 → `extractStatus: "SUCCESS"`
- 일부만 찾으면 → `extractStatus: "PARTIAL"` + 못 찾은 항목 목록(`missingFields`)
- 사용자는 빈 칸만 직접 채우면 됩니다.

> 🤔 **아무 URL이나 다 열어 주면 위험하지 않나요? (SSRF 방어)**
> 악의적 사용자가 `http://localhost`나 사내 IP(`192.168.x.x`)를 넣어 **서버 내부망을 들여다보려** 할 수 있습니다.
> 그래서 `validate()`에서 **http/https가 아니거나, localhost·사설 IP·내부망 주소면 차단**합니다. (`URL_NOT_ALLOWED`)

### 공고 등록 요청 예시

```http
POST /api/job-postings
Content-Type: application/json

{
  "companyName": "네이버",
  "title": "백엔드 개발자",
  "url": "https://recruit.navercorp.com/...",
  "position": "주니어 백엔드",
  "region": "판교",
  "startDate": "2026-06-01",
  "deadline": "2026-06-30",
  "techStacks": ["Java", "Spring Boot"],
  "description": "...",
  "initialStage": "APPLIED",      ← 등록 시 지원 기록의 시작 단계
  "confirmDuplicate": false       ← 같은 URL 중복 등록 방지
}
```

`companyName`과 `title`만 필수이고 나머지는 선택입니다.
같은 URL을 이미 등록했다면 `DUPLICATE_JOB_URL`(409)로 막습니다. (정말 또 등록하려면 `confirmDuplicate: true`)

## 7. Phase 3 — 지원 단계 추적

> **한마디**: "지원 → 서류 → 코딩테스트 → 면접 → 최종"으로 이어지는 **전형 단계를 바꾸고, 그 변경 이력을 남긴다.**

### 엔드포인트

| 메서드 | 경로 | 하는 일 |
|--------|------|---------|
| PUT | `/api/applications/{id}/stage` | 지원 단계 변경 (이력 자동 기록) |
| GET | `/api/applications/{id}/stage-histories` | 단계 변경 이력 전체 조회 |

### 13개의 지원 단계 (`ApplicationStage`)

| 단계 | 뜻 | 흐름 |
|------|-----|------|
| `INTERESTED` | 관심 공고 | 지원 전 |
| `PLANNED` | 지원 예정 | 지원 전 |
| `APPLIED` | 지원 완료 | ★ 지원 시작 |
| `DOCUMENT_PASS` | 서류 합격 | 서류 |
| `DOCUMENT_FAIL` | 서류 불합격 | 서류 (탈락) |
| `CODING_TEST` | 코딩테스트 진행 | 코테 |
| `CODING_PASS` | 코딩테스트 합격 | 코테 |
| `CODING_FAIL` | 코딩테스트 불합격 | 코테 (탈락) |
| `INTERVIEW` | 면접 진행 | 면접 |
| `INTERVIEW_PASS` | 면접 합격 | 면접 |
| `INTERVIEW_FAIL` | 면접 불합격 | 면접 (탈락) |
| `FINAL_PASS` | **최종 합격** | 끝 🎉 |
| `WITHDRAWN` | 지원 철회 | 끝 |

### 단계를 바꾸면 자동으로 일어나는 일

단계 변경(`changeStage`) 한 번에 **3가지**가 동시에 처리됩니다.

```
PUT /api/applications/5/stage
{ "toStage": "DOCUMENT_PASS", "memo": "서류 합격! 코테 준비하자" }

        ▼ 서버가 자동으로 ▼

① 현재 단계 변경        APPLIED → DOCUMENT_PASS
② 최종 결과 자동 갱신    finalResult = IN_PROGRESS (아직 진행 중)
③ 이력 한 줄 추가        [APPLIED → DOCUMENT_PASS, "서류 합격!", 2026-06-19 10:30]
```

**② 최종 결과(`finalResult`)는 단계에 따라 자동으로 정해집니다:**

| 바뀐 단계 | 최종 결과 |
|-----------|-----------|
| `FINAL_PASS` | `FINAL_PASS` (최종 합격) |
| `DOCUMENT_FAIL` / `CODING_FAIL` / `INTERVIEW_FAIL` | `REJECTED` (불합격) |
| `WITHDRAWN` | `WITHDRAWN` (철회) |
| 그 외 모든 단계 | `IN_PROGRESS` (진행 중) |

> 🤔 **이력(history)을 왜 따로 남기나요?**
> "현재 단계"만 저장하면 *과거에 어떻게 흘러왔는지*는 사라집니다.
> `APPLIED → DOCUMENT_PASS → INTERVIEW`처럼 **변경 때마다 한 줄씩 쌓아** 두면,
> 나중에 "나는 보통 어느 단계에서 떨어지는가" 같은 분석이 가능합니다. (Phase 5+ 대시보드의 밑거름)

> 📌 **참고**: 처음 공고를 등록할 때도 시작 단계로 이력 첫 줄이 자동으로 생깁니다(`null → APPLIED`).
> 그리고 단계가 `APPLIED` 이상이 되는 순간 `appliedAt`(지원 시각)이 자동 기록됩니다.

## 8. Phase 4 — 문서 관리

> **한마디**: 이력서·자기소개서를 **버전별로** 올리고, PDF에서 텍스트를 뽑아내고, "어느 공고에 어떤 버전을 냈는지" 연결한다.

### 3단 구조: 문서 → 버전 → 연결

```
Document (논리적 문서)          예: "나의 백엔드 이력서"
   │
   ├── DocumentVersion v1       resume_v1.pdf  (2026-05 작성)
   ├── DocumentVersion v2       resume_v2.pdf  (2026-06 수정)
   └── DocumentVersion v3       resume_v3.pdf  (최신)
                                     │
                                     └── ApplicationDocument
                                         "v3을 네이버 지원에 제출함"
```

> 🤔 **왜 '문서'와 '버전'을 나누나요?**
> 이력서는 계속 고쳐 씁니다. 매번 새 문서로 만들면 관리가 안 됩니다.
> "이력서"라는 **하나의 묶음(Document)** 아래에 **여러 버전(Version)** 을 두면,
> "이 회사엔 v2를, 저 회사엔 v3을 냈다"처럼 깔끔하게 추적됩니다.

### 엔드포인트

| 메서드 | 경로 | 하는 일 |
|--------|------|---------|
| POST | `/api/documents` | 문서(묶음) 생성 — 제목·종류만 |
| GET | `/api/documents` | 내 문서 목록 |
| GET | `/api/documents/{documentId}` | 문서 상세 + 버전 목록 |
| POST | `/api/documents/{documentId}/versions` | **파일 업로드** (PDF/TXT) |
| GET | `/api/document-versions/{versionId}/download` | 파일 다운로드 |
| DELETE | `/api/document-versions/{versionId}` | 버전 삭제 |
| POST | `/api/applications/{applicationId}/documents/{versionId}` | **공고에 이 버전을 제출했다고 연결** |

### 문서 종류 (`DocumentType`)

| 값 | 뜻 |
|----|-----|
| `RESUME` | 이력서 |
| `COVER_LETTER` | 자기소개서 |

### 파일 업로드는 어떻게 동작하나

`POST /api/documents/{documentId}/versions` 에 **multipart/form-data**로 파일을 보내면:

```
1. 검사    확장자(.pdf/.txt) + MIME 타입 둘 다 확인 → 아니면 UNSUPPORTED_FILE_TYPE
2. 저장    파일명을 UUID로 바꿔 저장 (예: a1b2c3...-d4e5.pdf)
3. 지문    SHA-256 해시 계산 (같은 파일인지 식별용)
4. 추출    PDFBox로 PDF 텍스트 뽑기 (TXT는 그대로 읽기)
5. 기록    원본명·저장명·경로·크기·해시·추출텍스트를 DB에 저장
```

응답에는 `extractStatus`가 들어갑니다.
- 텍스트를 뽑았으면 `"SUCCESS"`
- 못 뽑았으면(스캔된 이미지 PDF 등) `"FAILED"` — 사용자가 직접 입력하거나 다른 파일을 올리면 됩니다.

> 🤔 **왜 파일명을 UUID로 바꾸나요? (보안 §7.3 · §12.1)**
> 사용자가 올린 이름을 그대로 경로에 쓰면 두 가지 위험이 있습니다.
> ① `../../비밀파일.txt` 같은 이름으로 **경로를 벗어나는 공격**(Path Traversal),
> ② 같은 이름끼리 **덮어쓰기**.
> 그래서 저장 이름은 UUID로 만들고, 원래 이름·경로·종류·크기는 **DB에 메타데이터로만** 둡니다.
> 또 확장자뿐 아니라 **실제 형식(MIME)** 까지 확인해 위장 파일을 거릅니다.

> 🤔 **추출한 텍스트를 왜 따로 저장하나요?**
> 이 텍스트는 Phase 5+에서 **AI가 면접 질문을 만들 때** 재료로 씁니다.
> 매번 PDF를 다시 여는 건 느리니, 업로드할 때 한 번 뽑아 `extractedText`에 저장해 둡니다.

### DocumentVersion 엔티티 (버전 하나의 정보)

| 필드 | 설명 |
|------|------|
| `versionName` | 버전 이름 (예: "v1", "최종") |
| `description` | 메모 |
| `originalName` | 사용자가 올린 원본 파일명 |
| `storedName` | 서버에 저장된 UUID 이름 |
| `filePath` | 실제 저장 경로 |
| `mimeType` | `application/pdf` 또는 `text/plain` |
| `sizeBytes` | 파일 크기 |
| `hash` | SHA-256 지문 |
| `extractedText` | 추출된 텍스트 (AI 재료) |

## 10. 보안 한눈에 정리

이 프로젝트가 지키는 보안 원칙들입니다.

| 원칙 | 어떻게 |
|------|--------|
| 비밀번호를 안 가진다 | 소셜 로그인(카카오·구글) **전용** |
| 토큰 탈취 방지 | JWT를 **HttpOnly 쿠키**로 발급 |
| 내 것만 본다 | 모든 리소스에 **소유권 검증** (남의 것은 404) |
| 내부망 보호 | URL 미리보기 시 **SSRF 차단** (localhost·사설 IP 거부) |
| 파일 위장 방지 | **확장자 + MIME** 이중 검사, **UUID** 저장명 |
| 실수 복구 | 진짜 삭제 대신 **Soft Delete** (`deleted_at`) |
| 비밀값 분리 | DB 비밀번호·OAuth 키는 코드가 아닌 **환경변수(.env)** 로만 |
