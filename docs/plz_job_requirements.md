## 2. 프로젝트 배경 및 문제 정의

개발자 취업 준비생은 여러 채용 사이트에서 공고를 확인하고, 기업별로 다른 이력서와 자기소개서를 제출하며, 코딩테스트·면접·합격 여부를 개별적으로 관리한다. 이 과정에서 공고 URL, 마감일, 지원 서류 버전, 전형 단계, 회고 기록이 메모·스프레드시트·캘린더 등에 분산되는 문제가 있다.

또한 개인의 지원 현황만으로는 현재 채용 시장에서 어떤 기술 스택과 지역의 수요가 높은지, 본인의 지원 패턴이 시장 흐름과 어떻게 다른지 파악하기 어렵다.

본 프로젝트는 취업 공고와 개인 지원 이력을 한곳에서 관리하고, 공공 채용 데이터를 분석하여 시장 동향과 개인 지원 활동을 비교하며, 로컬 LLM을 활용해 예상 면접 질문과 데이터 분석 리포트를 생성하는 것을 목표로 한다.

## 3. 프로젝트 목표

### 3.1 핵심 목표

1. 취업 공고 URL 또는 직접 입력을 통해 지원 공고를 간편하게 등록한다.
2. 공고별 지원 단계, 일정, 결과, 회고를 CRUD 방식으로 관리한다.
3. 이력서와 자기소개서 파일을 공고별·버전별로 관리한다.
4. 업로드한 지원 서류와 공고 내용을 기반으로 로컬 LLM이 예상 면접 질문을 생성한다.
5. 개인 지원 기록과 공공 채용 데이터를 동적인 차트로 시각화한다.
6. Python 기반 ETL 파이프라인으로 데이터를 수집·전처리·Hadoop 적재·Oracle 집계한다.
7. 소셜 로그인과 권한 검증을 적용하여 사용자별 데이터를 안전하게 분리한다.

### 3.2 차별성

- 단순 공고 스크랩 서비스가 아니라 지원 과정 전체를 기록하는 개인 취업 CRM
- 개인 지원 데이터와 실제 채용 시장 데이터를 비교하는 분석 기능
- 외부 상용 AI API가 아닌 Ollama 로컬 LLM 기반 문서 분석
- 대시보드 차트를 LLM이 자연어로 해석하는 자동 리포트 기능
- Hadoop과 Oracle을 함께 사용하는 Raw Data·분석 데이터 분리 구조

## 4. 프로젝트 범위

### 4.1 1주일 필수 MVP

| 우선순위 | 기능 | 구현 범위 |
|---|---|---|
| 상 | 로그인 및 사용자 분리 | 카카오·구글 소셜 로그인 2종, JWT 또는 HttpOnly Cookie 인증 |
| 상 | 지원 공고 CRUD | URL 입력, 자동 추출 가능한 항목 자동 입력, 수동 수정, 조회·수정·삭제 |
| 상 | 지원 단계 관리 | 관심, 지원 예정, 지원 완료, 서류, 코딩테스트, 면접, 최종 합격, 불합격 |
| 상 | 대시보드 | 월별 지원 수, 단계별 전환 현황, 합격률, 기술 스택, 지역별 채용 데이터 |
| 상 | LLM 면접 질문 생성 | 공고 내용과 업로드 문서를 바탕으로 예상 질문 및 꼬리질문 생성 |
| 상 | LLM 차트 해석 | 대시보드 집계 데이터를 자연어 리포트로 생성 |
| 상 | 공공데이터 ETL | Open API 수집 → Python 전처리 → HDFS 적재 → 집계 → Oracle 적재 |
| 상 | Hadoop 연동 | Python ETL 적재 및 Spring Boot 조회 또는 상태 확인 연동 |
| 중 | 지원 서류 버전 관리 | PDF 또는 TXT 업로드, 버전명·업로드일·공고 연결 관리 |
| 중 | 회고 기록 | 코딩테스트·면접 유형별 회고 CRUD |
| 중 | 전형 일정 | 전형 예정일 등록 및 월간 또는 목록형 일정 표시 |


### 4.2 제외 범위

- 기업 인사 담당자용 채용 관리 기능
- 실제 입사 지원서 자동 제출
- 무단 로그인이 필요한 사이트 크롤링
- 사이트 이용약관이나 robots 정책을 위반하는 대규모 크롤링
- LLM이 생성한 결과를 실제 합격 가능성으로 보장하는 기능
- 일주일 내 모델 파인튜닝 또는 대규모 머신러닝 학습

## 5. 사용자 및 접근 권한

### 5.1 사용자 유형

| 역할 | 설명 | 주요 권한 |
|---|---|---|
| 비회원 | 로그인하지 않은 사용자 | 서비스 소개, 로그인 화면 접근 |
| 일반 사용자 | 소셜 로그인한 취업 준비생 | 자신의 공고, 서류, 일정, 회고, 분석 결과 관리 |

### 5.2 권한 정책

- 일반 사용자는 본인이 생성한 데이터만 조회·수정·삭제할 수 있다.
- URL의 식별자를 임의로 변경해도 다른 사용자의 데이터에 접근할 수 없어야 한다.
- 파일 다운로드 전에 파일 소유자 검증을 수행한다.
- LLM 요청 시 사용자가 소유한 공고와 문서만 프롬프트에 포함한다.

## 6. 핵심 사용자 시나리오

### 6.1 공고 등록 및 지원 관리

1. 사용자가 소셜 로그인한다.
2. 공고 등록 화면에서 공고 URL을 입력한다.
3. 서버가 허용된 Open API 또는 공개 페이지에서 회사명, 공고명, 마감일, 지역, 기술 스택을 추출한다.
4. 자동 추출에 실패한 항목은 사용자가 직접 입력하거나 수정한다.
5. 사용자가 지원 상태를 `지원 완료` 또는 `관심`, `지원 예정`으로 저장한다.
6. 전형 진행에 따라 지원 상태와 일정을 변경한다.
7. 최종 결과와 회고를 기록한다.

### 6.2 면접 질문 생성

1. 사용자가 공고 상세 화면에서 이력서 또는 자기소개서를 선택한다.
2. 서버가 파일에서 텍스트를 추출한다.
3. 공고 내용과 서류 내용을 Ollama에 전달한다.
4. LLM이 기술 질문, 경험 질문, 인성 질문과 각 질문의 꼬리질문을 생성한다.
5. 사용자는 생성 결과를 저장하거나 다시 생성할 수 있다.

### 6.3 데이터 분석 및 리포트 생성

1. Python ETL이 공공 채용 Open API 데이터를 수집한다.
2. 원본 데이터는 날짜별 경로로 HDFS에 적재한다.
3. 전처리 후 기술 스택, 지역, 공고일, 마감일 기준 집계 데이터를 생성한다.
4. 집계 결과를 Oracle 분석 테이블에 적재한다.
5. React 대시보드가 Spring Boot API로 집계 데이터를 조회한다.
6. 사용자가 `AI 분석하기`를 선택하면 차트의 수치와 비교 데이터를 Ollama가 해석한다.

## 7. 기능 요구사항

## 7.1 인증 및 사용자 관리

| ID | 요구사항 | 우선순위 | 완료 조건 |
|---|---|---:|---|
| AUTH-01 | 사용자는 카카오와 구글 소셜 로그인으로 가입·로그인할 수 있다. | 상 | 두 로그인 방식 모두 성공 후 서비스 메인 화면으로 이동한다. |
| AUTH-02 | 서버는 카카오 또는 구글 로그인 성공 시 사용자 정보를 Oracle에 저장하거나 갱신한다. | 상 | 동일한 공급자와 소셜 계정 식별자 조합은 중복 사용자로 생성되지 않는다. |
| AUTH-03 | 인증이 필요한 API는 인증 토큰 또는 세션을 검증한다. | 상 | 미인증 요청에 401을 반환한다. |
| AUTH-04 | 사용자는 로그아웃할 수 있다. | 상 | 인증 정보가 무효화되고 보호 페이지 접근이 차단된다. |
| AUTH-05 | 사용자는 닉네임, 희망 직무, 희망 지역, 주요 기술 스택을 관리할 수 있다. | 중 | 수정 후 대시보드와 프로필에 반영된다. |
| AUTH-06 | API는 데이터 소유권을 검증한다. | 상 | 타 사용자 데이터 접근 시 403 또는 404를 반환한다. |

## 7.2 취업 공고 및 지원 기록

| ID | 요구사항 | 우선순위 | 완료 조건 |
|---|---|---:|---|
| JOB-01 | 사용자는 공고 URL을 입력하여 공고 등록을 요청할 수 있다. | 상 | URL 형식이 검증되고 자동 추출 결과가 표시된다. |
| JOB-02 | 시스템은 회사명, 공고명, 공고 URL, 시작일, 마감일, 지역, 직무, 기술 스택을 저장한다. | 상 | 필수 필드 검증 후 Oracle에 저장된다. |
| JOB-03 | 자동 추출 결과를 사용자가 수정할 수 있다. | 상 | 수정된 값이 최종 저장된다. |
| JOB-04 | 자동 추출이 실패하면 수동 입력 화면을 제공한다. | 상 | URL만으로 저장이 막히지 않는다. |
| JOB-05 | 사용자는 자신의 지원 공고 목록을 조회할 수 있다. | 상 | 상태, 회사명, 직무, 기간별 필터가 적용된다. |
| JOB-06 | 사용자는 공고 상세 정보를 조회·수정·삭제할 수 있다. | 상 | 본인 소유 공고에 대해서만 동작한다. |
| JOB-07 | 사용자는 공고별 지원 상태를 변경할 수 있다. | 상 | 변경 이력이 저장되고 대시보드에 반영된다. |
| JOB-08 | 사용자는 즐겨찾기 또는 중요 공고 표시를 할 수 있다. | 하 | 목록 정렬 또는 필터에 반영된다. |
| JOB-09 | 동일 사용자가 같은 URL을 중복 등록하면 경고한다. | 중 | 중복 여부를 안내하고 저장 여부를 선택할 수 있다. |

### 지원 단계 코드

```text
INTERESTED       관심
PLANNED          지원 예정
APPLIED          지원 완료
DOCUMENT_PASS    서류 합격
DOCUMENT_FAIL    서류 불합격
CODING_TEST      코딩테스트 예정 또는 진행
CODING_PASS      코딩테스트 합격
CODING_FAIL      코딩테스트 불합격
INTERVIEW        면접 예정 또는 진행
INTERVIEW_PASS   면접 합격
INTERVIEW_FAIL   면접 불합격
FINAL_PASS       최종 합격
WITHDRAWN        지원 철회
```

## 7.3 서류 및 버전 관리

| ID | 요구사항 | 우선순위 | 완료 조건 |
|---|---|---:|---|
| DOC-01 | 사용자는 이력서 또는 자기소개서 파일을 업로드할 수 있다. | 중 | 허용된 확장자와 용량 검증 후 저장된다. |
| DOC-02 | 문서는 문서 유형, 버전명, 설명, 업로드일을 가진다. | 중 | 같은 문서에 여러 버전을 등록할 수 있다. |
| DOC-03 | 사용자는 공고에 사용한 문서 버전을 연결할 수 있다. | 중 | 공고 상세에서 제출 문서를 확인할 수 있다. |
| DOC-04 | 사용자는 문서를 다운로드하거나 삭제할 수 있다. | 중 | 소유권 확인 후 처리된다. |
| DOC-05 | 서버는 PDF 또는 TXT에서 텍스트를 추출할 수 있다. | 상 | LLM 질문 생성 입력으로 사용할 수 있다. |
| DOC-06 | 파일 원본과 추출 텍스트를 분리하여 저장한다. | 중 | 원본 재다운로드와 AI 처리가 모두 가능하다. |

### 파일 정책

- MVP 허용 확장자: PDF, TXT
- 권장 최대 크기: 파일당 10MB
- 실제 파일은 서버 로컬 저장소 또는 공유 볼륨에 저장한다.
- Oracle에는 파일 경로, 원본명, 저장명, MIME Type, 크기, 해시값 등 메타데이터를 저장한다.
- 업로드 파일명은 UUID 기반으로 변환하여 경로 조작과 파일명 충돌을 방지한다.

| DASH-04 | 공공데이터의 기술 스택 빈도 또는 추세를 표시한다. | 상 | 기간·직무 조건에 따라 차트가 갱신된다. |
| DASH-05 | 지역별 채용 공고 수를 지도 또는 막대 차트로 표시한다. | 상 | 지역 필터 및 툴팁을 제공한다. |
| DASH-06 | 개인 지원 기술 스택과 시장 기술 스택을 비교한다. | 상 | 동일 기준의 비교 차트로 표현된다. |
| DASH-07 | 차트 선택 또는 호버 시 상세 수치와 기준을 표시한다. | 상 | 툴팁 또는 상세 패널이 동작한다. |
| DASH-08 | 사용자는 기간, 직무, 지역, 기술 스택 조건을 변경할 수 있다. | 중 | 필터 변경 시 API를 다시 호출하고 화면이 갱신된다. |
| DASH-09 | 데이터가 없을 때 빈 화면 안내를 표시한다. | 상 | 오류와 데이터 없음 상태가 구분된다. |
| DASH-10 | 차트 데이터를 표 또는 CSV로 확인할 수 있다. | 하 | 차트와 동일한 데이터를 제공한다. |

### 지표 정의

- 월별 지원 수: 사용자가 해당 월에 `APPLIED` 이상 상태로 변경한 공고 수
- 서류 통과율: 서류 합격 수 ÷ 서류 결과가 확정된 지원 수 × 100
- 코딩테스트 통과율: 코딩테스트 합격 수 ÷ 코딩테스트 결과가 확정된 지원 수 × 100
- 면접 통과율: 면접 합격 수 ÷ 면접 결과가 확정된 지원 수 × 100
- 최종 합격률: 최종 합격 수 ÷ 최종 결과가 확정된 지원 수 × 100
- 시장 기술 스택 비율: 필터 조건에 해당하는 공고 중 특정 기술 스택이 포함된 공고 수 ÷ 전체 공고 수 × 100

분모가 0인 경우 비율을 0%로 표시하지 않고 `계산할 데이터가 부족합니다`로 표시한다.

### LLM 차트 해석 입력 원칙

LLM에는 전체 원본 데이터가 아니라 서버에서 계산한 다음 집계값만 전달한다.

- 기간
- 월별 지원 수
- 단계별 지원 수와 전환율
- 사용자 주요 기술 스택
- 시장 상위 기술 스택
- 지역별 공고 수
- 이전 기간 대비 증감률

이 방식으로 프롬프트 길이를 줄이고 잘못된 수치 계산을 방지한다. 수치 계산은 서버 또는 Python이 담당하고, LLM은 해석과 문장 생성을 담당한다.

## 7.7 데이터 수집 및 ETL

| ID | 요구사항 | 우선순위 | 완료 조건 |
|---|---|---:|---|
| ETL-01 | Python은 공공 채용 Open API 데이터를 수집한다. | 상 | 인증키와 요청 조건을 이용해 원본 응답을 저장한다. |
| ETL-02 | 수집 데이터의 중복, 결측치, 날짜, 지역, 직무명을 전처리한다. | 상 | 표준 스키마로 변환된다. |
| ETL-03 | 원본 데이터는 HDFS Raw 영역에 적재한다. | 상 | 수집 일자별 경로에 파일이 생성된다. |
| ETL-04 | 전처리 데이터는 HDFS Processed 영역에 적재한다. | 상 | CSV 또는 Parquet 형식으로 저장된다. |
| ETL-05 | 기술 스택·지역·기간별 집계 결과를 생성한다. | 상 | 분석용 데이터셋이 생성된다. |
| ETL-06 | 집계 결과는 Oracle 분석 테이블에 적재한다. | 상 | Spring Boot API로 조회할 수 있다. |
| ETL-07 | ETL 실행 결과와 오류를 로그로 저장한다. | 상 | 시작·종료 시각, 처리 건수, 성공 여부가 기록된다. |
| ETL-08 | 같은 공고를 다시 수집해도 중복 적재되지 않는다. | 상 | 외부 공고 ID 또는 URL 해시 기준으로 Upsert한다. |
| ETL-09 | 수집 실패 시 기존 분석 데이터는 유지한다. | 상 | 일부 실패가 전체 서비스 장애로 이어지지 않는다. |
| ETL-10 | Spring Boot는 ETL 상태 또는 최신 집계 기준일을 제공한다. | 중 | 대시보드에 데이터 기준일을 표시한다. |

### 공공데이터 후보

1. 고용24 또는 워크넷 채용정보 Open API
2. 공공기관 채용정보 Open API
3. 고용행정통계 Open API
4. 직업·직종·지역 코드 데이터

최종 데이터 소스는 신청 승인 여부, 호출 제한, 응답 필드, 비영리 이용 조건, 프로젝트 기간 내 발급 가능 여부를 확인하여 결정한다. 승인이 지연될 경우 공개 파일 데이터 또는 사전에 내려받은 샘플 데이터를 사용한다.

### ETL 처리 흐름

```text
[Open API / 공공데이터 파일]
            ↓ Extract
[Python requests 수집]
            ↓
[HDFS /plz-job/raw/수집일자]
            ↓ Transform
[Pandas 정제·표준화·기술 스택 추출]
            ↓
[HDFS /plz-job/processed/기준일자]
            ↓ Aggregate
[기술 스택·지역·월별 집계]
            ↓ Load
[Oracle analytics_* 테이블]
            ↓
[Spring Boot REST API]
            ↓
[React 동적 대시보드 + Ollama 해석]
```

### HDFS 디렉터리 예시

```text
/plz-job/raw/source=work24/collected_date=2026-06-16/
/plz-job/raw/source=public_jobs/collected_date=2026-06-16/
/plz-job/processed/base_date=2026-06-16/
/plz-job/aggregate/base_date=2026-06-16/
/plz-job/error/run_date=2026-06-16/
```

### 전처리 규칙

- 문자열 앞뒤 공백 및 HTML 태그 제거
- 날짜 형식을 `YYYY-MM-DD`로 통일
- 지역명을 시·도와 시·군·구로 분리
- 직무명을 백엔드, 프런트엔드, 풀스택, 데이터, AI, 모바일, DevOps, 기타로 표준화
- 기술 스택은 사전 기반으로 추출하고 동의어를 통합
- 예: `SpringBoot`, `Spring Boot` → `Spring Boot`
- 예: `React.js`, `ReactJS` → `React`
- 공고 식별자는 외부 ID가 있으면 외부 ID를 사용하고, 없으면 URL 해시를 사용
- 원본 값과 표준화 값을 함께 보존

## 9. 시스템 구성

```text
React Front-End
   ├─ 인증 화면
   ├─ 공고·서류·회고 CRUD
   ├─ 대시보드 차트
   └─ AI 결과 화면
          ↓ REST API
Spring Boot Back-End
   ├─ Spring Security
   ├─ 사용자·공고·서류·일정·회고 API
   ├─ 분석 조회 API
   ├─ 파일 처리
   ├─ URL 파싱
   ├─ Ollama Client
   └─ Hadoop Client 또는 WebHDFS Client
       ↓                ↓                 ↓
    Oracle          Hadoop HDFS        Ollama
 업무·집계 데이터     Raw/Processed 데이터   질문·리포트 생성
       ↑
Python ETL
   ├─ Open API 수집
   ├─ Pandas 전처리
   ├─ HDFS 적재
   └─ Oracle 집계 적재
```

### 구성 원칙

- Oracle: 사용자 서비스와 빠른 화면 조회에 필요한 정형 데이터 저장
- Hadoop HDFS: 공공데이터 원본, 전처리 파일, 집계 산출물 보관
- Python: 데이터 수집·정제·집계 담당
- Spring Boot: 인증, 비즈니스 로직, 데이터 제공, Ollama 연동 담당
- React: 사용자 입력, 동적 시각화, AI 결과 표현 담당
- Ollama: 수치 계산이 아닌 문서 기반 질문 생성과 분석 문장 생성 담당

### 10.2 데이터 무결성

- 소셜 계정 식별자에 Unique 제약을 적용한다.
- 공고 URL은 사용자 단위로 중복 인덱스를 검토한다.
- 자식 데이터는 부모 사용자 또는 공고 삭제 정책에 맞추어 처리한다.
- 실제 삭제 대신 `deleted_at`을 이용한 소프트 삭제를 적용할 수 있다.
- 분석 집계 테이블은 기준월·직무·지역·기술 스택 조합에 Unique 제약을 적용한다.
- 모든 주요 테이블에 생성일과 수정일을 저장한다.

## 12. 비기능 요구사항

### 12.1 보안

- Spring Security를 적용한다.
- 인증이 필요한 API는 로그인 여부와 소유권을 모두 검증한다.
- 비밀번호를 직접 저장하지 않고 소셜 로그인 식별정보만 저장한다.
- JWT를 사용할 경우 만료 시간을 적용하고, 브라우저 저장 위치를 보안 정책에 맞게 결정한다.
- 가능하면 인증 토큰은 Secure·HttpOnly·SameSite 속성이 적용된 쿠키로 전달한다.
- 파일 확장자뿐 아니라 MIME Type과 실제 파일 형식을 확인한다.
- 업로드 경로에 사용자 입력 파일명을 직접 사용하지 않는다.
- URL 수집 기능은 SSRF 방지를 위해 허용 프로토콜, 도메인, IP 대역을 검증한다.
- SQL Injection 방지를 위해 Prepared Statement 또는 ORM 바인딩을 사용한다.
- XSS 방지를 위해 공고 HTML과 사용자 입력을 정제한다.
- OAuth Secret, 공공데이터 인증키, DB 비밀번호는 환경변수로 관리한다.
- LLM 프롬프트와 응답에 포함된 개인정보를 일반 로그에 남기지 않는다.

### 12.2 성능

- 일반 목록 API는 3초 이내 응답을 목표로 한다.
- 대시보드는 원본 HDFS 파일을 실시간 전체 조회하지 않고 Oracle 집계 테이블을 조회한다.
- LLM 생성은 일반 API와 분리하여 로딩 상태와 타임아웃을 처리한다.
- 목록 API는 페이지네이션을 적용한다.
- 차트 데이터는 필요한 필드만 반환한다.

### 12.3 신뢰성

- 외부 API 또는 Ollama 장애가 공고 CRUD 전체 장애로 이어지지 않아야 한다.
- AI 생성 실패 시 사용자가 기존 공고와 문서를 계속 조회할 수 있어야 한다.
- ETL 실패 시 직전 성공 집계 데이터를 유지한다.
- 모든 외부 연동에는 타임아웃과 예외 처리를 적용한다.

### 12.4 사용성

- 모바일과 데스크톱에서 사용할 수 있는 반응형 화면을 제공한다.
- 저장·삭제·AI 생성·파일 업로드의 진행 상태를 표시한다.
- 오류 메시지는 사용자가 해결할 수 있는 문장으로 표시한다.
- 차트에는 제목, 단위, 기간, 데이터 기준일, 표본 수를 표시한다.
- 색상만으로 상태를 구분하지 않고 텍스트 또는 아이콘을 함께 사용한다.

### 12.5 AI 품질

- 생성형 AI 결과에 사실 보장 문구를 사용하지 않는다.
- 수치 계산은 LLM이 아니라 Python 또는 Spring Boot에서 수행한다.
- LLM 응답 스키마를 검증한다.
- 공고 또는 문서 내용에 질문 생성을 방해하는 명령이 포함되어도 시스템 프롬프트를 우선하도록 한다.
- 면접 질문의 근거 필드를 제공하여 사용자가 생성 이유를 확인할 수 있게 한다.

## 13. 머신러닝 적용 검토

일주일 프로젝트에서는 사용자별 합격 예측 모델을 핵심 기능으로 두지 않는다. 사용자 기록이 충분하지 않아 학습 데이터가 부족하고, 합격 여부에는 정량화하기 어려운 변수가 많기 때문이다.

대신 다음과 같은 설명 가능한 분석을 권장한다.

1. 기술 스택 빈도 분석
2. 월별 기술 스택 증감률
3. 직무별 공고 군집 또는 키워드 분석
4. TF-IDF 기반 공고 핵심 키워드 추출
5. 사용자 보유 기술과 시장 요구 기술의 일치율 계산

시간이 남을 경우 공고 설명을 벡터화하여 유사 공고를 찾는 기능을 확장할 수 있다. 이 경우 결과를 합격 가능성이 아니라 `공고 내용 유사도`로 명확히 표현한다.

| 채용 사이트 크롤링 차단 | URL 자동 입력 실패 | Open API 우선, 수동 입력 fallback, 허용 도메인만 지원 |
| Ollama 모델 속도 저하 | 시연 지연 | 작은 모델 사용, 입력 길이 제한, 응답 토큰 제한 |
| PDF 텍스트 추출 실패 | 질문 생성 불가 | TXT 지원, 텍스트 직접 입력 fallback |
| Hadoop 접속 문제 | ETL 시연 실패 | 접속 정보를 첫날 검증, 로컬 샘플과 실행 로그 보관 |
| 분석 표본 부족 | 비율 왜곡 | 표본 수 표시, 분모 0 처리, 예측 대신 기술통계 사용 |
| 기능 과다 | 통합 미완성 | 상 우선 기능을 먼저 완료하고 캘린더·버전 관리는 후순위로 조정 |
| 보안 구현 지연 | 개인정보 노출 위험 | 소유권 검증과 파일 접근 제어를 우선순위 상으로 지정 |
| 팀별 데이터 형식 불일치 | 통합 지연 | 첫날 공통 JSON·DB·집계 스키마 확정 |

## 20. 최종 MVP 권장안

일주일 프로젝트에서 발표 완성도를 높이기 위한 최종 핵심 범위는 다음과 같다.

### 반드시 구현

1. 카카오·구글 소셜 로그인 2종
2. 공고 URL 자동 입력과 수동 보정
3. 개인 지원 공고 CRUD
4. 지원 단계 변경과 이력 저장
5. 공공데이터 Python ETL
6. HDFS Raw·Processed 적재
7. Oracle 분석 집계 적재
8. 월별 지원, 단계별 통과율, 기술 스택, 지역별 채용 차트
9. 공고와 PDF/TXT 기반 예상 면접 질문·꼬리질문
10. 차트 수치 기반 AI 분석 리포트
11. 사용자별 접근 권한과 파일 보안

### 시간이 남으면 구현

1. 이력서·자기소개서 다중 버전 관리
2. 코딩테스트·면접 회고 CRUD
3. 전형 캘린더
4. AI 생성 이력 저장

이 범위는 FE의 동적 시각화와 LLM 활용, DA의 Hadoop 연계 ETL, BE의 Spring Boot·DB·Hadoop·보안·Ollama 연동을 모두 하나의 시연 흐름으로 연결한다.
